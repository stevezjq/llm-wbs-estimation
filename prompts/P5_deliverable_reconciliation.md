# P5 交付物对账框架 v1.0

你是资深软件项目经理。请把下面的需求拆解为 WBS 工作包，并用三点法估时。你的首要任务是**按可验收交付物组织工作包**，避免把同一份交付物拆成多个包重复计工。

{{REQUIREMENT}}

【第一步：交付物对账（不输出，仅供你内部推理）】
1. 按需求章节与功能点，列出全部可独立验收的交付物（功能模块、接口、页面、测试报告、部署包、文档等）。
2. 一个交付物对应一个工作包；同一交付物不得拆成多个工作包分别计满工时。
3. 只有当子项本身可独立验收（如“后端接口”与“前端页面”、“检测插件”与“扫描报告”）时才拆分。
4. 目标包数应与交付物数相近，而不是与活动数相近；少于 3 人时的碎片并入相邻工作包。

【第二步：隐性工作检查】
依次以以下视角审阅，确认是否需要独立工作包，**不得默认省略**；已被功能包吸收的工作不要重复单列：
1. 需求与设计：需求澄清、验收口径、架构与数据模型、接口定义。
2. 开发：全部功能实现、前后端内部联调。
3. 测试：功能、兼容、性能、缺陷修复、试运行整改。
4. 安全与合规：审计留痕、越权与口令、安全测试/评审、合规材料。
5. 交付与运维：用户文档、离线或容器化部署、监控与备份、版本管理。
6. 管理：例会、进度跟踪、评审组织。
若某类确实不适用，须在 `assumptions` 写明理由。

【第三步：估时与自检】
1. 单位为人时（person-hour），指完成该工作包的净人工投入；不考虑组织级因素（采购、法务、跨部门协调）。
2. `optimistic`：一切顺利、无返工、依赖及时到位；`pessimistic` 只覆盖任务内典型返工与外部依赖延迟，不含极端风险。
3. 必须满足 `optimistic ≤ most_likely ≤ pessimistic`，且 `hours = most_likely`。
4. 常规工作包 4–8 人时；确属不可再分的时间块可至 10 人时，并在 `assumptions` 说明原因；超过 10 人时须拆成可独立验收的子交付物。
5. 输出前自检：
   - 是否存在同一交付物对应多个工作包？若有，合并并合并工时。
   - 包数是否明显多于交付物数？若是，合并同类活动。
   - 是否有仅因拆分而保留、合并后不足 3 人时的包？
   - `depends_on` 是否只引用本次输出、无悬空/自引用/成环？

【输出格式】
只输出一个合法 JSON 对象，不要输出解释性文字，不要使用 Markdown 代码围栏。
